5 дыр в сайте от ИИ: как найти и закрыть

Клод собирает сайт за вечер, но пять дыр встречаются снова и снова. Ниже — как проверить каждую самому, команда /security-review и промпт, которым Клод проверит весь проект. Сверено с документацией Claude Code, октябрь 2026.

  1. 01

    Быстрая проверка перед отправкой

    В Claude Code набери /security-review. Клод сравнит твою ветку с веткой на GitHub и разберёт изменения: ключи в коде, инъекции, вход и права, утечки данных. У каждой находки — опасность и совет.

    Нужен git и проект на GitHub (remote origin). Команда смотрит только новые изменения — то, что уже лежит на GitHub, она не проверит. Для этого — промпт ниже.

    Нашёл дыры — напиши «исправь» и проверь, что сайт работает.

  2. 02

    Промпт: проверить весь проект

    Открой Claude Code в папке проекта и вставь:

    Проверь весь проект на безопасность — не только последние изменения. Пройди по пунктам: 1) ключи, токены и пароли в коде, который уходит в браузер (фронтенд, переменные с префиксами NEXT_PUBLIC_ и VITE_); 2) можно ли открыть чужие данные, поменяв id в ссылке или запросе — сервер должен проверять, чьи это данные; 3) проверки входа и прав, которые есть только в браузере; 4) запросы к базе, склеенные из текста пользователя (SQL-инъекции); 5) как хранятся пароли пользователей — должен быть только хэш (bcrypt или argon2). Если в проекте Supabase — проверь, что на каждой таблице включён RLS и есть политики. По каждой находке: файл и строка, чем опасно, насколько срочно. Ничего не меняй, пока я не напишу «исправь».
  3. ДЫРА 1

    Ключ от API в коде страницы

    Как проверить: открой свой сайт, нажми F12 → вкладка Sources (или «Источники») и поищи по коду sk-, key, token. Что видишь ты — видит любой.

    Как правильно: ключ живёт только на сервере в .env, а .env — в .gitignore. Страница просит твой сервер, сервер ходит в API.

    Ключ уже засветился — перевыпусти его в кабинете сервиса. Старый считай чужим.

  4. ДЫРА 2

    Чужой заказ по номеру в ссылке

    Как проверить: заведи два тестовых аккаунта. Под первым открой свой заказ, профиль или файл и поменяй число в ссылке. Открылось чужое — дыра.

    Как правильно: сервер на каждый запрос проверяет, что заказ принадлежит тому, кто вошёл. Скрытая кнопка в интерфейсе не защищает.

  5. ДЫРА 3

    Пароль админки проверяется в браузере

    Как проверить: F12 → Sources, поищи admin, password, isAdmin. Пароль или проверка роли в коде страницы — дыра: код страницы можно прочитать и обойти.

    Как правильно: вход и права проверяет сервер, страница только показывает результат.

  6. ДЫРА 4

    SQL-инъекция через поиск или форму

    Как проверить: попроси Клода найти места, где запрос к базе собирается из текста пользователя через + или шаблонную строку.

    Как правильно: параметризованные запросы или ORM — текст пользователя никогда не становится частью команды для базы.

  7. ДЫРА 5

    Пароли пользователей открытым текстом

    Как проверить: открой таблицу пользователей в базе. Если в колонке пароля читаются qwerty123 и 12345 — беда: при утечке базы их увидят все, а люди ставят те же пароли на почту.

    Как правильно: хранить только хэш (bcrypt или argon2) и сбросить старые пароли.

  8. БОНУС

    Supabase без RLS

    В 2025 исследователь проверил 1 645 приложений из витрины Lovable: у 170 таблицы базы читались без входа — не был включён RLS (CVE-2025-48757).

    Как проверить: в панели Supabase открой Advisors → Security Advisor — он подсветит таблицы без RLS. Включи RLS и добавь политики «пользователь видит только своё».

  9. ВАЖНО

    Прежде чем проверять

    • Проверяй только свои сайты. Чужие — без разрешения владельца нельзя.
    • Клод тоже ошибается: после «исправь» прогони проверку ещё раз и пощёлкай сайт руками.
    • Сайт с деньгами или чужими персональными данными — покажи специалисту по безопасности.
